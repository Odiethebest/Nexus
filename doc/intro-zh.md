# 用大白话理解 Nexus

## 这是干什么的

Nexus 是一个通知中枢。

你的系统只要发出一次事件，比如订单支付成功，Nexus 就会把这条事件分发到不同渠道，比如邮件、应用内消息、Webhook。

你可以把它理解成一个专门负责通知投递的中心服务。

## 为什么需要它

很多项目一开始都在业务代码里直接发通知，后面常见的问题是：

- 第三方接口慢，主流程被拖住
- 临时故障时通知会丢
- 重试没处理好，容易重复发送

Nexus 的作用就是把这些问题集中治理，让通知链路更稳定。

## 页面怎么用

打开 Dashboard 后，主要看左右两块。

左边是发布事件。

- Type 表示事件类型，比如 order、payment、alert
- Priority 表示优先级，分 high、normal、low
- Payload 是 JSON 格式的事件内容
- Publish 按钮用于发送事件

第一次体验可以直接粘贴这段内容。

```json
{"user_id":"u123","email":"user@example.com"}
```

右边是实时通知流。

点击发布后，右侧会出现新卡片，显示事件类型、优先级、payload 和时间。

如果右上角是 Connected，说明实时连接状态正常。

## 两分钟快速上手

1. Type 填 order
2. Priority 选 high
3. 粘贴示例 JSON
4. 点击 Publish
5. 确认右侧出现新卡片
6. 把优先级改成 normal 再发一次
7. 把优先级改成 low 再发一次

做到这里，你已经跑通了最核心的使用流程。

## 常见问题

- 点发布后没反应：先检查 JSON 是否合法，字符串是否用了双引号
- 页面显示 disconnected：发布通常仍可用，但实时更新可能有延迟
- 不知道 Type 填什么：先用 order，再试 payment、refund

## 你能得到的价值

- 一次事件可以分发到多个渠道
- Webhook 失败会自动重试
- Redis 幂等机制减少重复处理
- PostgreSQL 保存投递历史，方便排查和审计

## 一个真实例子

在电商场景里，订单支付后可以同时做到：

- 给用户发邮件回执
- 在 App 内展示一条新消息
- 把事件推给 CRM 系统

而你的业务侧只需要发布一次事件。
